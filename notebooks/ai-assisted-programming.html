AI-assisted programming in biology#

Learning goals

By the end of this chapter you should be able to

  • Use a coding assistant to understand unfamiliar code and get unstuck when writing your own

  • Decide when to ask for help and how much of the work to hand over

  • Start from a biological question, decide what you want the code to do and check whether it does what you intended

  • Explain what a result tells you about the biology and which decisions it depends on

  • Decide what you can share with an assistant and keep a record of your work, including how you used its help, so someone else can reproduce it

Prerequisites

It helps to know how to run a Python script from a terminal and to be able to follow a short function that reads or summarises a table. Revisit Biological Computing in Python or UNIX and Linux if you need a refresher.

For the survey exercises, you’ll need Python 3, a text editor and a terminal. You can work with the prepared suggestions in the practice folder. Some of the self-study exercises also use Jupyter, R, Bash or Git. Check the setup for the exercise you choose.

Introduction#

Why learn to programme when you can ask an AI assistant to write the code for you?

This is a fair question, especially if you’ve ever spent more time getting a table into R than looking at what’s in it!

An AI assistant can show you how to read an unfamiliar file, help you make sense of an error message, or give you a first draft of a plotting script. All of that can save you time.

Now suppose you’re comparing animal activity at two sites, and you spent twice as long watching at one of them. What would be a fair comparison? You could get a dozen lines of perfectly good Python that add up the counts for each site. The interesting bit is deciding what those counts mean when the amount of time you spent watching differs. That decision goes into the analysis whether you write the code yourself or ask for help.

This is where the habits from our Python, R and algorithms chapters come in handy. Work out what you’d expect for a small example, then see whether the program gives you the same answer. If it doesn’t, you have somewhere to start looking. We’ll use a small field survey to try this out with a chat reply, a suggestion in the editor, and an agent that can edit a file and run a check.

Remember#

The six headings in this chapter follow the revised Bloom taxonomy. They describe the thinking you do. When you remember, you recall a rule or idea. By the time you create, you are combining ideas into a design you can explain and check. In practice you will go back and forth. You might recall a Python function halfway through reviewing a design. See Krathwohl (2002) and MQB’s algorithms chapter for the connection to specifying and checking a problem.

What is a large language model?#

A large language model (LLM) learns patterns from examples of language, including code. It represents text as tokens, which can be words, parts of words or punctuation. Given some tokens, it estimates probabilities for what token could come next. Generating a line of Python involves repeating this step. A completion can look familiar because the same pattern has worked somewhere before. You still need to check what it does with your inputs.

Understand#

How are code models trained?#

During pre-training, a model learns statistical patterns from large collections of text and code. It can learn that a loop often follows a line ending with a colon, and that files of the same type tend to be read in similar ways. A developer can then fine-tune the model for particular tasks. Instruction tuning uses examples of requests and desirable responses so a model is more likely to follow a request such as “explain this loop”. Some models also use feedback to shape their responses.

What the model learned during training can go out of date. Check the documentation for the version you’re using when a suggestion depends on a new library or changed option. A coding assistant can also retrieve files or documentation using tools. That new information becomes part of the context for the request. A retrieval result can itself be incomplete or out of date. Check its source and the version it describes.

One example of an open instruction-tuning dataset is NVIDIA’s OpenCodeInstruct. Its examples include requests, solutions and information about checks. Look at the dataset’s field names and ask which kinds of coding tasks will be represented well, and which are likely to need more examples or specialist judgement. Dataset card and licence

What does the assistant receive?#

A request has space for only so much information. The assistant may also include instructions, conversation, selected files and the results of tools. A long session may summarise or omit earlier material. Restate the assumptions that your analysis depends on and inspect the attached context before sending it. VS Code context guide

Chat, editor assistance and agents#

We’ll use the three scenarios from CodeRefinery. As you read through them, ask what you’re handing over to the assistant and what you’ll work out for yourself. That second question is where Bloom comes in.

Scenario I · Chat#

In manual chat, you choose what to send and decide which parts of the reply to try. Ask a question such as “How could a cancelled watch end up in the denominator?” In Understand, you’ll explain why two replies disagree. In Apply, you can try a hint on a case you’ve worked out by hand. Once a suggestion is in your editor, run it on an example you already know the answer to.

Scenario II · Editor assistance#

An assistant in your editor can use information from your code to suggest a completion or an edit. In Apply, you’ll predict what a completion does when a count is zero or a rate is unavailable, then run your check. That check gives you something to go on when you Evaluate whether to keep a suggestion.

Scenario III · Agents#

An agent can use tools to read files, edit code and run commands. What it can do depends on the tools and permissions you give it. In Analyse, you’ll read its plan and inspect a proposed change. In Evaluate, you’ll use your checks to decide which changes you would keep.

The same editor can offer all three. When you reach Create, decide what you want to calculate and write a check first. Then choose whether a question in chat, a suggested line or an agent edit would help you try out your design.

GitHub Copilot in VS Code provides a concrete example. The documented Copilot harness offers Ask, Plan via /plan, and Agent. The model and available actions depend on the account and settings. Start with the model offered by your account and review the session’s context and permissions. For current setup details, see the VS Code Copilot appendix. For inline assistance in RStudio, follow Copilot in RStudio. VS Code agent controls · GitHub plans

Apply#

State the goal, your attempt, the help you want and the check you will use. For example, ask for help reviewing the calculation in pooled_rate, give the inputs and expected behaviour, and ask to keep the rest of the script intact. Read the reply or completion, then run a hand-derived check in a new process. Keep to the same scientific question if you switch between manual chat, an editor or a prepared candidate.

Evaluate#

Can I trust the result? May I share the context? What can the tool do?#

These questions are about research integrity, confidentiality and security. A plausible result can mislead a reader if the wrong rows go into a calculation. A file can include unpublished findings, identifying information or credentials. An assistant with tools can also act on commands, files or dependencies. A file may contain instructions that the tool reads along with the data. Treat that text as data, review the action it proposes and decline actions outside your task.

The same case can raise all three questions. An over-permissioned assistant could read a restricted survey, send material to a service and write a changed input file. Using synthetic data, keeping the original inputs protected and checking the final output address different parts of that risk. Verify unexpected packages against the package registry and original project, including why the package is needed, before you consider installing anything.

Check separately what your tool sends, where it is processed, what is retained, whether people can review it and whether it is used for training. These answers depend on the service, account and configuration. An exclusion setting has feature-specific coverage. Keep restricted material outside the practice folder and check permission before sending research material to any service. A local model still needs a check of its editor, tools and network connections.

Create#

Before requesting an implementation, decide what each part of the calculation represents. State the question, write down the inputs, the returned rows, the ordered steps and a case you can check. This gives you something against which to evaluate a proposed design. In science, two working implementations may give different answers because they answer different questions.

Create · Which rate would you report?#

You want to compare sites where completed watches vary in length. Choose the question to answer.

  • How many visits did we see per minute of observation across the completed watches?

  • What was the average of the rates for individual completed watches, with each watch contributing equally?

Decide which summary to use for a comparison you can explain. State units, how you handle a cancelled watch and what you report with no observed effort. Use Meadow or invent a case with unequal durations and different watch-specific rates. Work out both values by hand before you ask for help. Keep the existing reader and test files intact. In either case, design how the report will tell a reader which calculation it used. Try your change in a separate copy and write a check that would detect a switch between the two calculations.

Hint

Pooling gives each observed minute equal weight. Averaging rates gives each completed watch equal weight. How much influence does a five-minute watch have under each rule?

Candidate approaches

For pooling, accumulate visits and observed minutes, then divide. For equal weight by watch, compute a rate inside the completed-watch condition and keep a sum and count of those rates for each site, then divide by the count of completed watches. Keep the label or method with the value so a reader knows which calculation you used.

Worked explanation

Pooling Meadow gives (0 + 3) / (5 + 10) = 0.2 visits per minute. The mean of the watch rates gives (0 / 5 + 3 / 10) / 2 = 0.15 visits per minute. Either can represent a well-defined summary. State which calculation supports the question you chose and show which prediction your check expects. These rates describe visits during the watches and depend on the sampling design.

        raise ValueError("window must be an integer >= 6")
    if not math.isfinite(extinction_threshold) or extinction_threshold < 0:
        raise ValueError("Invalid extinction threshold")
    if not math.isfinite(equilibrium_tolerance) or equilibrium_tolerance < 0:
        raise ValueError("Invalid equilibrium tolerance")

def lv_rates(state, r=1.0, a=0.1, z=0.2, e=0.1, K=50.0):
    resource, consumer = state
    return (r*resource*(1-resource/K) - a*resource*consumer,
            -z*consumer + e*a*resource*consumer)

def lv_trace(initial, steps=500, dt=0.05):
    state = tuple(initial)

    for _ in range(steps):
        k1 = lv_rates(state)

Both plots have two recorded species. The repeated record of a does not add a species. The difference in effort matters when you interpret the two observed counts. The table gives no estimate of unrecorded species.

AI-assisted version control · Analyse → Evaluate#

Optional self-study · 25–30 minutes. You need Git and Python 3. If working with the staging area feels unfamiliar, read Version control with Git before you start.

Imagine a colleague has asked you to show observed minutes alongside the pollinator visit rate. A coding assistant has edited the report. Another change is in the same file. Which parts of the diff would you put in a commit to your colleague?

Download the pollinator Git practice repository. Extract it into a new directory and open the extracted pollinator-git folder. It already contains a local repository with a baseline commit. Open a terminal there. Run:

git status --short
git log -1 --oneline
git diff -- code/summarise_watches.py

Analyse · 10 minutes. Read the whole diff before opening the summary. A hunk is a group of nearby changed lines and their surrounding context. Write down what each hunk changes. Which change affects what is printed, and which could affect a calculated value? Then open the summary and identify what it missed.

Prepared AI summary · Open after reading the diff

“The change adds an observed_minutes column to the report and fills it from the per-site totals. It does not change which watches contribute to the calculation or the existing rate.”

This was prepared with AI for the exercise and deliberately leaves out one part of the diff.

Evaluate · 15–20 minutes. Predict the Meadow result under the original rule. A completed watch contributes its observed minutes even if the count is zero. Rerun the supplied completed-zero check on the changed report:

python checks/check_watches.py --show-minutes

Explain whether the result supports the summary. Stage just the change you would keep. Read each hunk when prompted and decide whether to stage it:

git add -p -- code/summarise_watches.py
git diff --staged -- code/summarise_watches.py
git diff -- code/summarise_watches.py

If both changes appear together, enter s to split the hunk when Git offers that option. Check that the staged diff describes your intended change and that the other hunk is still in the unstaged diff. Draft a one-line commit message from what is staged. Stop with the draft and the two reviewed diffs. Keep the working-tree check and the staged diff distinct when you explain what you found.

Hint · If you get stuck

A completed watch with zero flower visits contributes zero to the numerator. What does it contribute to the denominator? In git add -p, you can answer y to stage a hunk and n to leave it unstaged. Use the diff to choose which answer applies to each hunk.

Worked explanation · Open after staging and drafting

The summary missed the new and visits > 0 condition. It leaves out the five-minute completed watch that had zero visits. The working tree reports Meadow as three visits in ten minutes instead of three in fifteen. The supplied check fails on that change. If you staged just the report hunk, the staged diff shows a new column and the value printed for it. The unstaged diff still shows the faulty filter, so a run from the working tree still tests both edits. A suitable draft is “Report observed minutes alongside pollinator visit rates”.
